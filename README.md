# Ускорение синхронизации сущностей из CRM в Postgres

Точка входа — `collect_leads_customers(is_full=True)`. Синхронизация обрабатывает покупателей и сделки пакетами (`BATCH_SIZE = 1000`), сохраняя `JSONB`-структуру сущностей и поддерживая быстрый поиск и связи через индексные таблицы.

## Что было дорого в исходном подходе
- Отдельные SQL-запросы и `db.session.commit()` на каждую сущность при объёмах 20 тыс. покупателей и 50 тыс. сделок.
- Повторное полное чтение таблицы в конце цикла и отсутствие индексных полей для быстрого поиска по ID CRM, логину и названию.
- Риск частичного применения изменений или удаления данных при сбое во время выгрузки.

## Что изменено
- **Батчевая обработка вместо поштучных коммитов:** в `main.py` введена обработка батчами (`BATCH_SIZE = 500`) с коммитами по батчам и очисткой кэша/сессии между ними.
- **Добавлены таблицы-связи и индексы (`models.py`):** `CustomerLink` и `LeadLink` с внешним ключом на `abstract_customer.id` (`ON DELETE CASCADE`) и индексами по `abstract_customer_id`, `login` и `name` — для поддержки связи «сделка — покупатель» и быстрого поиска по ID CRM, точному логину и названию.
- **Кэш индексов на время прохода (`SyncIndex` в `main.py`):** предзагрузка связей из БД в начале синхронизации убирает N+1 запросы при поиске покупателя по ID/логину сделок и сделки по ID/логину покупателей.
- **Исправлены правила бизнес-логики (`main.py`, `abstract_customer.py`):**
  - покупатель без логина пропускается;
  - при `> 1` совпадении по логину совпадение не используется;
  - при нахождении двух разных записей по сделке и по логину покупателя данные сливаются в запись по сделке, а запись покупателя удаляется;
  - при `is_full=True` удаление отсутствующих записей и вложенных сущностей с «удалить» в имени (без учёта регистра) запускается только если оба этапа выгрузки (покупатели и сделки) завершились без ошибок.
- **Безопасная сериализация и доступ к полям (`amocrm.py`):** в `BaseEntity` добавлен метод `as_dict()` и защита `get_field()` от `None` в `custom_fields_values`.

## Что оставлено и почему
- **Формат JSONB-полей в `AbstractCustomer` (`amo_customers`, `amo_leads`, `amo_companies`, `amo_contacts`, `send_methods`):** сохранён для обратной совместимости с существующей моделью данных и потребителями.
- **Стек (`Python >= 3.9`, `Flask`, `SQLAlchemy`, `PostgreSQL`) и синхронный `amocrm_get`:** оставлены в рамках ограничений задания без добавления Celery, брокеров очередей, новых сервисов и боевого API.

## Оценка на 20 тыс. покупателей и 50 тыс. сделок
- **Число запросов к PostgreSQL:** порядка **150–300 запросов** за полный прогон (первичная загрузка связей через `SELECT`, точечные обращения по PK в батчах по 500 записей, ~140 батч-коммитов и удаление отсутствующих записей в конце) вместо сотен тысяч запросов и коммитов на каждую сущность.
- **Память процесса:** словари индексов и увиденных ID в `SyncIndex` занимают около **15–25 МБ**; за счёт очистки кэша и `db.session.expire_all()` раз в 500 записей пиковое потребление памяти процесса оценивается в **~60–140 МБ** (в зависимости от размера `api_value` в JSONB).
